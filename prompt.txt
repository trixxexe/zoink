ZoinK — TUI Song Downloader + Web Music Player

You are building ZoinK, a polished, minimalistic TUI-first music downloader designed especially for Termux/Linux users.

This is a real project, not a toy/demo. I want you to make strong engineering decisions autonomously, inspect existing code before changing it, and continuously keep the architecture clean.

Product Vision

ZoinK should feel like a peak terminal-native music application:

- Minimalistic TUI
- Extremely fast navigation
- Search for songs
- Preview useful metadata
- One-key/one-action download
- High-quality embedded metadata
- Full album artwork embedded into files
- Full lyrics embedded when available
- Album/artist metadata
- Batch/bulk downloads
- Beautiful browser-based music player
- Local web server
- Browser player should work extremely well on a phone
- Browser player must also have download functionality
- Bulk downloading from the browser should be easy
- Downloads should ultimately land somewhere practical on the user's device
- Termux users should not have to fight with "mv", "cp", storage paths, or awkward file management

The philosophy is:

«Search → select → download → listen.

No unnecessary complexity.»

TUI Navigation

Support sensible keyboard controls.

At minimum:

- Arrow keys / vim keys for navigation
- Enter = select
- "/" or a dedicated key = search
- "d" = download
- "a" = album
- "A" = artist/album actions where appropriate
- "b" = bulk/batch actions
- "p" = preview/details
- "q" = quit
- Esc = back/cancel

Show context-sensitive key hints.

Don't make users memorize obscure controls.

---

Search

Implement a proper search abstraction.

The downloader/search provider must NOT be tightly coupled to the TUI.

Create a provider abstraction so the backend can be replaced later.

Conceptually:

SearchProvider
    ├── search tracks
    ├── search albums
    ├── resolve track
    ├── resolve album
    └── retrieve media

Search results should expose useful normalized metadata:

- title
- artist
- album
- album artist
- duration
- release date/year
- track number
- disc number
- artwork
- lyrics availability
- source
- stable identifier

Never make the UI understand provider-specific response formats.

Downloads

A single action should download a song.

Example flow:

Search
  ↓
Select track
  ↓
Download
  ↓
Resolve media
  ↓
Download audio
  ↓
Fetch metadata
  ↓
Fetch artwork
  ↓
Fetch lyrics
  ↓
Embed everything
  ↓
Write final file

The final output should be a polished music file, not merely a raw audio stream.

Metadata

Metadata quality is a major feature.

Where available, embed:

- Title
- Artist
- Album
- Album Artist
- Composer
- Genre
- Release date
- Year
- Track number
- Disc number
- Total tracks
- Total discs
- Copyright
- Comment

Use the correct tagging format for the selected output container.

---

Album Artwork

Download the highest-quality appropriate album artwork available.

Embed it directly into the final audio file.

Do not merely save:

cover.jpg

unless the user explicitly requests external artwork.

Artwork should be embedded.

Handle:

- missing artwork
- invalid artwork
- oversized artwork
- unusual MIME types
- transparent images
- network failures

Gracefully.

---

Lyrics

Fetch lyrics where available.

Prefer full lyrics rather than snippets.

Embed lyrics into the file using the appropriate metadata mechanism for that format.

Lyrics failures must NOT cause an otherwise successful download to fail.

For example:

Audio       ✓
Metadata    ✓
Artwork     ✓
Lyrics      —

should still produce a valid downloaded track.

Do not fabricate lyrics.

---

Audio Formats

Design the system so formats are configurable.

At minimum, architect support for common formats such as:

- MP3
- M4A
- FLAC
- Opus

Do not assume that every source can provide every format.

Clearly separate:

Source format
      ↓
Decoder / remuxer / transcoder
      ↓
Output format
      ↓
Metadata embedding

Avoid unnecessary transcoding.

If a lossless/remux-compatible path exists, prefer it.

Do not silently destroy audio quality.

---

Quality

Make quality configurable.

For example:

Quality
  Best available
  Lossless
  High
  Medium

Do not hardcode a single quality choice.

The configuration system should make this extensible.

Download Manager

Downloads should be managed through a dedicated subsystem.

Support:

- concurrent downloads
- configurable concurrency
- progress
- cancellation
- retry
- resume where technically possible
- duplicate detection
- safe temporary files
- atomic finalization
- failed-download cleanup

Never leave half-written files pretending to be completed downloads.

Prefer:

track.tmp
   ↓
verify
   ↓
embed metadata
   ↓
rename atomically
   ↓
track.ext

Support selecting multiple tracks.

Also support:

Browser Download UX

This is particularly important for Termux users.

The web interface should make downloading files to the phone as frictionless as possible.

The browser should receive proper:

- Content-Disposition
- MIME type
- filename
- range support where useful

For multiple files, investigate the best practical browser-compatible approach.

For example:

Download selected
        ↓
ZIP / archive generation
        ↓
browser download

if that provides a better experience.

Do not force users to manually copy files around inside Termux.

---

Termux

Treat Termux as a first-class environment.

Do not assume:

- systemd
- desktop Linux
- "/home/user"
- root access
- privileged ports

The application should behave naturally in Termux.

Document the recommended Termux storage setup.

Do NOT blindly run commands that modify Android storage permissions.

Instead, detect common Termux situations and provide clear instructions when required.

Where possible, make the application work with a user-selected output directory.

---

Server Security

The web server is local software, but do not treat security casually.

By default:

- bind only to localhost unless explicitly configured
- do not expose arbitrary filesystem access
- sanitize all paths
- prevent path traversal
- validate download identifiers
- do not expose secrets/configuration
- avoid arbitrary command execution
- don't trust client-provided filenames

If LAN access is explicitly enabled, make that choice obvious.

Keep the web frontend independent from internal downloader implementation.

Potential endpoints:

Adapt this to the actual framework/language.

Do not blindly implement endpoints that aren't necessary.

---

Streaming

The browser player should stream local music rather than requiring a complete download first.

Support HTTP range requests so seeking works properly.

Don't load entire large audio files into memory.

Use streaming I/O.

Database / Library

- downloaded tracks

- metadata
- albums
- artists

- lyrics state

Do not introduce a database just because databases are cool.

Error Handling

Errors should be human-readable.

Bad:

Error: request failed

Better:

Couldn't fetch artwork.

Reason:
The artwork provider timed out.

The track itself downloaded successfully.

Classify failures where practical:

- network
- provider
- authentication
- unavailable media
- metadata
- filesystem
- permissions
- transcoding
- corrupted media

A failure in an optional enhancement should not necessarily fail the entire download.

Dependencies

Before adding a dependency:

1. Determine whether the standard library already solves the problem.
2. Check whether the dependency is maintained.
3. Check its license.
4. Check whether it works on Termux.
5. Consider binary size and startup time.
6. Consider whether it introduces unnecessary complexity.

Prefer mature, boring dependencies over trendy ones.

Provider Architecture

Treat external music/media providers as unreliable.

Provider failures should not crash the entire application.

Create clean interfaces around them.

Do not scatter provider-specific assumptions throughout the codebase.

If provider implementations already exist in the repository, inspect them carefully before replacing them.

---

Legal / Responsible Design

ZoinK is a downloader/player application.

Do not implement DRM circumvention.

Do not bypass authentication or access controls.

Do not design around defeating provider restrictions.

Respect provider terms and copyright requirements.

The architecture should allow legitimate sources and user-authorized media.

ZoinK should feel instant.

Pay attention to:

- startup time
- TUI rendering
- search latency
- memory usage
- concurrent downloads
- streaming
- large libraries
- artwork handling
- metadata parsing

Avoid loading an entire music library into memory if it becomes large.
